# Семинар 6. Отмена корутин и structured concurrency

## Задание 1. Отмена установки приложения

**Что сделано:**
- Введён `InstallState` (NotInstalled / Installing(progress) / Installed).
- В `AppDetailsState.Content` добавлено поле `installState`.
- В `AppDetailsViewModel` заведено приватное `installJob: Job?`.
- `onInstallClick()`:
    - если `installState is Installing` → `installJob?.cancel()`, состояние → `NotInstalled`;
    - иначе → `installJob = viewModelScope.launch { emulateInstall() }`.
- `emulateInstall()` — цикл `0..100 step 5` с `delay(150)`, обновление через `_state.update`.
- Кнопка «Установить» → «Отменить (N%)» при установке, «Установлено» — по завершении.
- `onCleared()` отменяет job при уничтожении ViewModel (structured concurrency).

**Наблюдения:**
- `cancel()` прерывает `delay()` мгновенно — `CancellationException` пробрасывается и корутина завершается.
- Состояние возвращается в `NotInstalled` синхронно в обработчике кнопки, до отмены джобы — это безопасно, потому что отменённая джоба уже ничего не запишет в `_state` (её `update` не выполнится после `cancel`).
- `installJob` живёт в `viewModelScope` → автоматически отменяется при смерти экрана.

## Задание 2. Загрузка рейтингов в каталоге

**Способы:**

1. **Последовательно** (`getRatingsSequentially`):
   обычный `for` с `suspend`-вызовом `getRating` внутри — каждый следующий запрос стартует только после завершения предыдущего.

2. **Параллельно без ограничений** (`getRatingsInParallel`):
   `coroutineScope { ids.map { async { id to getRating(id) } }.awaitAll().toMap() }` — все запросы стартуют одновременно, ждём все через `awaitAll`.

**Замеры (список из 10 приложений, эмуляция задержки 1500 мс):**

| Способ            | Время выполнения |
|-------------------|------------------|
| Последовательно   | ≈ 15 000 мс      |
| Параллельно       | ≈ 1 500 мс       |

> Фактические числа могут колебаться ±100 мс из-за планировщика. Соотношение ~10× — прямое следствие того, что последовательный вариант выполняет 10 запросов по 1.5 с, а параллельный — 10 запросов одновременно.

**Выводы:**
- Параллельный вариант даёт ускорение, кратное числу элементов (при достаточном пуле потоков Dispatchers.IO).
- При большом числе элементов параллельный «без ограничений» может перегрузить сеть/сервер/потоки → на практике нужен `Semaphore` или `Dispatchers.IO.limitedParallelism(n)`.
- `coroutineScope` обеспечивает structured concurrency: падение одной корутины отменяет остальные и пробрасывает исключение.
- Для UI-сценариев (загрузка рейтингов в каталоге) параллельный вариант предпочтителен — пользователь видит данные почти сразу.

## Ключевые концепции (ответы на вопросы семинара)

- **Concurrency** — про *структуру* программы: много задач «в работе» одновременно, но не обязательно в один момент времени (переключение контекста на одном ядре).
- **Параллелизм** — про *физическое одновременное* выполнение на нескольких ядрах.
- **Многопоточность** — механизм реализации concurrency в рамках одного процесса (потоки делят память → data race, deadlock).
- **Асинхронность** — способ не блокировать поток, пока ждём результат (callbacks, корутины).
- **Корутина** — лёгкая «задача» внутри потока; `suspend`-функция может приостановиться, не блокируя поток.
- **Structured concurrency** — корутины образуют иерархию (родитель-ребёнок); отмена/исключение распространяются по дереву; `viewModelScope` отменяет всех детей при `onCleared`.
